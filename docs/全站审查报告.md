## 一、总体结论

| 维度 | 评价 |
| --- | --- |
| 架构 | 每章「引擎 / 课程 / 界面」分离清楚，纯前端、无 CDN、无账号、可离线双击打开。 |
| 算法正确性 | 每个引擎都有对应测试文件，关键约定（逻辑位置 1 起、带头节点、闭/半开区间等）在文档中写明。 |
| 状态模型 | 每步保存独立执行后快照，回退按快照恢复，整体执行到位。 |
| 交互完整度 | 单步、回退、播放、调速、预测、关键点暂停、时间线、日志跳转齐备。 |
| 一致性 | **九份页面壳层靠手工复制**，已出现可观测的漂移（见 P1-3）。 |
| 可访问性 | 首页与链表页做得最好；后五章在 tab 语义与 `noscript` 上有缺口，次要文字对比度全站偏弱。 |
| 性能 | 算法章存在明显的每步全量重建与日志全量渲染，长轨迹会卡。 |
| 可维护性 | 多处 HTML/CSS 被压成超长单行，源码不可读、diff 不可审。 |

一句话：**内容与算法底子很扎实，问题主要不在「算得对不对」，而在「九个页面各自长大」带来的漂移、移动端可达性、以及算法章的性能与日志体验。**

## 二、问题清单

严重度定义：P0＝影响正常使用或结果可信度；P1＝明显影响体验/一致性；P2＝工程与长期维护。

### P0

**P0-1 算法章代码区不跟随高亮，且每一步重建整块代码 DOM**
位置：`js/algorithm-render.js:31`
`render()` 每次都用 `t.code.map(...)` 重新拼字符串并写入 `$('code').innerHTML`，而图、树、串、排序都在切换步骤时只切换 `.active` 类并调用 `scrollTop` 跟随（如 `js/graph-app.js:20`、`js/tree-app.js:29`、`js/string-app.js:24`、`js/sort-render.js:17`）。算法章全文件没有 `scrollTop` / `scrollIntoView`。
影响：C 代码面板 `#code{max-height:680px;overflow:auto}`，轨迹一长，高亮行在可视区外，用户只能手动找；同时每步重建上百行 DOM，播放明显变慢。
建议：轨迹加载时渲染一次代码，`render()` 里只做 `active` 类切换 + 滚动跟随；课程区 `$('lesson')` 同理只渲染一次。

**P0-2 算法章执行日志一次性生成全部步骤按钮**
位置：`js/algorithm-app.js:5`
`log()` 对 `trace.steps` 全量 `createElement('button')`。运行层允许最多 70000 步（`js/algorithm-runtime.js:7`），意味着极端情况下一次生成 7 万个按钮节点。
影响：长轨迹首次渲染卡顿、内存占用高，甚至页面假死；这与「最多 70000 步」的保护目标冲突。
建议：只渲染当前步附近窗口（如 ±150 步）+「跳到开头/结尾」，或改成虚拟列表；日志容器用事件委托而不是每项一个 `onclick`。

**P0-3 移动端「清除本章记录」入口消失**
位置：`styles.css:7`（`@media(max-width:720px){... .side-bottom{display:none}}`）
只有 `linked.html:69` 和 `stack-queue.html:53` 在页脚补了 `#mobile-clear`。`index`、`string`、`tree`、`graph`、`search`、`sort`、`algorithm` 七页在 ≤720px 时侧栏底部被隐藏，页面内没有第二个清除入口。
影响：手机用户无法清除本章记录，只能清浏览器站点数据；与 README「可从侧边栏清除」的说明不符。
建议：把「清除记录」做成页脚常驻按钮（或设置面板），九页统一。

**P0-4 存档结构损坏会让整页脚本中断（tree / string）**
位置：`js/tree-app.js:1`、`js/string-app.js:2`
两处都是 `const completed = new Set(saved.completed || [])`。若 `localStorage` 中该键是 `{"completed": 5}` 这类非数组值，`new Set(5)` 抛 `TypeError`，且不在 `try` 内，整个 IIFE 中止——按钮全部失效、演示不再生成。
对照：`js/stack-queue-app.js:7-8`、`js/algorithm-app.js:1`、`js/search-app.js:1`、`js/app.js:8-9` 都先做了 `Array.isArray` 校验。
影响：一次版本变更或手工改存储即可造成「白屏但页面还在」的故障，且没有提示。
建议：统一 `const list = Array.isArray(saved.completed) ? saved.completed : []`，并过滤非法项；可抽成共享的 `safeProgress()`。

**P0-5 完成度把失败分支算作「已完成」**
位置：`js/tree-app.js:30`、`js/string-app.js:25`
两处在 `s.done` 时直接 `completed.add(...)`。树的建表第 k 次申请失败、串的容量不足返回 0 都是 `done`，也会计入「算法演示已完成」。
对照：`js/linked-app.js:201` 要求 `s.result`，`js/sort-app.js:6` 要求 `trace.result.ok`。
影响：进度虚高，学习者把失败分支当成已掌握；也破坏「成功完成的操作才计数」的既有口径（README「完成一次成功的操作演示会标记对应操作」）。
建议：统一为「成功」判定（引擎暴露 `ok/result`），失败分支单独记「已练习」。

### P1

**P1-1 预测面板会被重复点击「下一步」重置**
位置：`js/app.js:152-156`、`js/linked-app.js:215-217`、`js/search-app.js:34`、`js/tree-app.js:35`、`js/sort-app.js:12`
这些页面在预测模式下每次调用 `next()` 都重新 `askPrediction()/prediction()`：重建选项、清空反馈、隐藏「揭示」按钮。用户答对后再点一次「下一步」，已答状态丢失。
对照：`js/string-app.js:28` 有 `if(pending!==null) return;`，图章节 `js/graph-app.js:22` 有 `if(prediction) return;`。
影响：预测流程像是「点了没反应/被重置」，是高频操作路径。
建议：统一守卫（预测进行中忽略 `next`），并把「揭示」设为唯一前进方式；抽成共享的播放状态机。

**P1-2 键盘快捷键在按钮聚焦时失效**
位置：`js/app.js:194-199`、`js/linked-app.js:267-272`（其它章同样把 `BUTTON` 列入排除名单）
点击「下一步」后焦点留在按钮上，此时 ←/→/空格全部无效；README 也写明「当焦点不在输入或按钮上时」。用户点一下就必须再点空白处才能用键盘。
影响：键盘学习流的连续性被打断；对只用键盘的用户接近不可用。
建议：只对 `INPUT/SELECT/TEXTAREA`（以及 `contenteditable`）屏蔽；按钮上按 ←/→/空格 仍执行播放器动作，或点击后 `blur()`。

**P1-3 九份页头/导航/页签手工复制，已经漂移**
证据（同一功能，不同写法）：
- tab 语义：`index.html:38-41`、`linked.html:31-35` 有 `aria-controls`/`aria-selected`；`tree.html:5`、`graph.html:5`、`search.html:7`、`sort.html:2`、`algorithm.html:6` 没有；`stack-queue.html:26`、`string.html:4` 只有 `aria-controls` 没有初值。
- 无脚本提示：只有 `index/linked/stack-queue/string` 有 `<noscript>`，后五页没有。
- 图标：`index/linked` 用内联 SVG favicon，其余 7 页是 `href="data:,"`（空白图标）。
- 缓存参数：`graph.html:1` 给 CSS 和 3 个 JS 都加了 `?v=0.6.0-final`，`stack-queue.html:7` 只给 app.js 加 `?v=0.3.0`，其余页面没有。
- 顶栏分隔：`graph/search/sort/algorithm` 用「·」分隔，`index/linked/stack-queue/string/tree` 用间距。
影响：修一个导航要改九处，已经漏了 aria 与 noscript；缓存参数不一致会让更新后部分用户拿到旧脚本。
建议：新增 `js/site-shell.js`，用一份章节数据渲染侧栏、顶栏与页签（纯 DOM，无需构建）；或至少在 CI 里加一个「九页结构一致性」检查。

**P1-4 次要文字对比度与字号不足**
位置：`styles.css:2` 令牌 `--muted:#798692`，`styles.css:3` 大量 9–11px 规则（如 `.side-caption{font-size:11px}`、`.brand-sub{font-size:8px}`）；`graph.css:1` 用 `color:var(--muted)` 渲染说明段落。
计算：`#798692` 在白色上的对比度约 **3.7:1**，低于 WCAG AA 正文 4.5:1；`algorithm.css` 中 `.cell small` 的 `#8b9b92` 约为 **2.9:1**。
影响：长时间阅读的说明文字偏灰偏小，408 学习场景下易疲劳；视力不佳用户难以辨认。
建议：说明文字改用 ≥4.5:1 的灰（如 `#5c6b77`），字号不低于 12px；索引类小字可保留但不要承载关键信息；补一次 axe/Lighthouse 检查。

**P1-5 文案与状态标记互相矛盾**
- `stack-queue.html:49`：「共享栈、双端队列、表达式求值、**表达式求值**和图等为后续规划」——重复词，且「图」早已开放（`graph.html` 存在，README 也列为已开放）。
- `index.html:22-23`、`index.html:25`：栈队列、串、图已是「已开放 ↗」，却仍带 `class="chapter planned"`；`linked.html:20-22` 同样。
- `README.md:3` 按「九个章节」计数，而侧栏目录是「01 / 08」（链表算作 01 的子项）。两种口径都能自圆其说，但同页并存时容易让人以为漏了一章。
影响：新手会误以为章节还没做；维护者也会困惑 `planned` 到底表示什么。
建议：`planned` 只用于真正未开放的入口；补一个「开放性由数据驱动」的导航；统一章节计数口径。

**P1-6 首页功能明显落后于其它八章**
`index.html` 没有：快速示例按钮（「快速试试」）、执行记录面板、暂停点选择、C 代码下载、「用结果继续操作」。
影响：作为入口页，体验反而最弱；用户第一印象是「这页比后面简陋」。
建议：把链表/栈队列的这五项能力回填到顺序表（引擎已有完整快照与 `source`，改造成本低）。

### P2

**P2-1 `linked.css` 实际是共享壳层样式，命名却绑定链表**
`string.html:1`、`tree.html:1` 都加载 `linked.css`；`stack-queue.html:6` 同时加载 `styles.css`、`linked.css`、`stack-queue.css`，`body` 也复用 `class="linked-page"`。
影响：改链表页样式可能连带改变串、树、栈队列；新人很难判断某条规则的归属。
建议：拆出 `shell.css`（布局、侧栏、播放器、属性面板），链表专属规则留在 `linked.css`。

**P2-2 源码被压成超长单行，无法评审**
`string.html` 全文 11 行、`styles.css` 9 行（首行装有整站基础样式，长达数千字符）、`sort.html`/`algorithm.html` 同样大量单行。
影响：无法做有意义的 diff，代码审查、合并冲突、定位行号都困难；本次审查也只能按选择器/函数名定位。
建议：源文件恢复为正常换行（体积差异在 gzip 后可忽略，且这是离线单机站点），或保留源码可读、发布时再压缩。

**P2-3 进度分母写死**
`js/algorithm-app.js:2`（`/44`、`/36`）、`js/string-app.js:3`（`/20`）、`js/search-app.js:3`（`/32`）、`js/sort-app.js:2`（`/20`、`/30`）、`js/graph-app.js:3`（`/12`）。
影响：一旦增删题目或算法，进度显示会说谎。
建议：全部改为 `Object.keys(L.catalog).length` / `C.quizzes.length`。

**P2-4 缺深链与状态恢复**
所有页面都靠内存变量保存当前算法与步骤，刷新即回到默认；无法分享「KMP 第 12 步」。
建议：用 `location.hash` 保存 `#op=kmp&step=12`，页面加载时恢复；对教学分享很有价值。

**P2-5 部署与安全加固缺口**
- 无 `Content-Security-Policy`（虽然是纯静态站，仍可作为纵深防御）。
- 7 页缺 `<meta name="description">`；无 `theme-color`。
- 无 Service Worker，README 的「离线」仅在本地双击成立，GitHub Pages 断网不可用。
建议：加 meta CSP（`default-src 'self'; style-src 'self' 'unsafe-inline'`）、补 description；若要真离线，加 manifest + 简单 SW 缓存。

**P2-6 测试只覆盖引擎，没有交互回归**
`tests/` 下 9 个 `*.test.cjs` 覆盖各引擎；但「预测重置」「移动端清除入口」「算法代码滚动」这类问题只有浏览器测试能发现。
建议：引入 Playwright（本地 `file://` 即可），每章保留 2–3 条冒烟：加载无报错 → 生成 → 下一步 → 回退 → 切页签 → 预测答对。
另：`package.json:7` 的 `node --test tests/*.test.cjs` 依赖 Node 22+ 的通配符支持或 shell 展开；在 Windows `cmd.exe` 下不会展开，建议改为 `node --test tests`。

**P2-7 文档漂移**
`docs/实施计划.md` 只记录到树章（2026-11-05），图、查找、排序、算法四章没有对应条目；README 的章节数与侧栏编号不一致（P1-5）。
建议：实施计划按章补齐，或改为「当前状态」表。

**P2-8 预测选项的随机化方式九页各不相同**
- 链表：Fisher–Yates（`js/linked-app.js:241`，正确）。
- 顺序表：`sort(() => Math.random() - .5)`（`js/app.js:176`，分布有偏）。
- 字符串/树：按步数做确定性旋转（`js/string-app.js:28`、`js/tree-app.js:35`），正确项位置可被总结出规律。
- 排序：按字母序排列（`js/sort-app.js:11`），位置由文案决定。
影响：预测练习的「猜位置」收益不一致，部分页面会削弱练习本身的意义。
建议：统一成一个共享的 `shuffleChoices()`（Fisher–Yates），并保证正确项不在固定位置。

## 三、分章观察

各章算法正确性已有相当充分的证据：`work/github-upload-tests.log` 记录 73 项测试全通过，`docs/*验证记录.md` 还包含穷举与真实 C 对照。以下只列**页面与交互层**可直接改进的点，不重复引擎正确性结论。

### 3.1 顺序表（index.html / js/app.js）
- 输入校验、快照独立、错误时保留旧轨迹都做得扎实；tab 的 roving tabindex 与方向键处理较完整。
- 缺「快速试试 / 执行记录 / 暂停点 / 下载 C / 结果续用」五项，是九章中功能最少的页面（P1-6）。
- 文案细节：`readInteger` 的报错模板是 `` `${label}必须填写整数。` ``，实际显示「位置 i必须填写整数」（`js/app.js:52`、`54`），中英文间缺空格。
- `highlighted()` 先 `escape()` 再做 `\b\d+\b` 高亮（`js/app.js:15`），一旦 C 源码出现字符字面量，`&#39;` 里的 `39` 会被包进 `<span>` 破坏实体。当前源码没有单引号，属潜在问题；链表页同样写法（`js/linked-app.js:106`）。
- `drawArrow()` 在演示面板隐藏时 `getBoundingClientRect().width` 为 0（`js/app.js:143-146`），此时 resize 会算出异常坐标；建议宽度为 0 时直接跳过。

### 3.2 链表（linked.html / js/linked-app.js）
- 节点观察器、暂停点、申请失败分支、`reuse-result` 的 8 节点上限提示都处理得很细；SVG 节点 `tabindex=0` + Enter 可操作。
- 预测选项用 Fisher–Yates 洗牌（`js/linked-app.js:241`），是九页中最正确的做法，可作为统一实现。
- 点击节点会整图重绘（`js/linked-app.js:205`），节点多时略浪费；可只更新选中态。
- 页脚已有 `#mobile-clear`（`linked.html:69`），是移动端清除入口的正确样例。

### 3.3 栈与队列（stack-queue.html / js/stack-queue-app.js）
- 顺序栈 `top=0`、循环队列「front 队头 / rear 下一空位 / 预留一格」与 AGENTS 约定一致。
- `stack-queue.html:49` 的概念页文案有重复词，并把已开放的「图」写成后续规划（P1-5）。
- 分段选择器（`stack-queue.html:29`）没有 `aria-label` / `aria-pressed`，而链表页同类控件有（`linked.html:38`）。
- `showView()` 的 aria/tabIndex 逻辑正确（`js/stack-queue-app.js:20-23`），但标记里没有初值，首帧到脚本执行前语义不完整。

### 3.4 串（string.html / js/string-app.js）
- 输入限制为可打印 ASCII 32–126，`cell()` 用 `esc()` 输出（`js/string-app.js:16`），未发现注入点。
- 完成度把容量不足的失败也算完成（P0-5），存档未校验（P0-4），移动端无清除入口（P0-3）。
- 页面被压成 11 行（P2-2）；tab 缺 `aria-selected` 初值与 `aria-controls`（P1-3）。
- 预测选项用确定性旋转（`js/string-app.js:28`），正确项位置会随步数规律移动（P2-8）。

### 3.5 树与二叉树（tree.html / js/tree-app.js）
- 验证记录覆盖 65 种树形、155 个 C 场景，引擎层可信度高。
- 每一步都重建当前函数的 C 代码块（`js/tree-app.js:29`），虽有滚动跟随，但可像串/排序那样只渲染一次再切 `.active`（同类问题见 P0-1）。
- 完成度与存档两个问题同 P0-4/P0-5；预测选项同样用确定性旋转（`js/tree-app.js:35`）。
- 播放区把「预测 / 执行记录 / 结果续用」都塞进同一个 panel（`tree.html:13`），移动端信息密度偏高。

### 3.6 图（graph.html / js/graph-app.js）

## 六、安全面结论（针对「漏洞」）

先说结论：**没有发现可被远程利用的注入或越权问题**。这是一个纯静态、无账号、无网络请求的本地教学站，攻击面主要是「页面自己把自己弄坏」。

逐项核对：

| 面 | 结论 |
| --- | --- |
| 外部依赖 | 无 CDN、无字体、无 `fetch`、无 ES module，全部相对路径；断网可用。 |
| 用户输入进 DOM | 抽查各页渲染路径，顶点标签、字符串字符、记录身份、解释文本都经过 `esc()`；未发现用户可控字符串直接拼进 `innerHTML` 的可用路径。 |
| 转义纪律 | `js/algorithm-render.js:29-30` 的调用帧变量与返回值、`result()` 里的 `s.answer` 未转义；当前内置模型只产出数字/布尔，暂不可利用，但新增算法若把字符串放进 `vars` 就会变成注入点，建议统一 `esc()`。 |
| 生成的 C 代码 | `js/algorithm-engine.js:57` 只拼接内置源码与数值数组，不把用户字符串写进 C 字面量；下载文件不执行。 |
| 存储 | 仅 `localStorage` 本域数据，无跨用户内容；风险是结构损坏（P0-4）和公共电脑上的进度残留。 |
| 传输 | GitHub Pages 为 HTTPS；页面无表单提交、无第三方统计。 |
| 加固 | 无 CSP。可加 `<meta http-equiv="Content-Security-Policy" content="default-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; img-src 'self' data:">`（需保留内联 `style` 属性与 data URI 图标）。 |

因此本报告的「漏洞」重点放在**健壮性缺陷**（存档损坏 → 整页失效）、**状态机缺陷**（预测被重置、完成度虚高）和**可达性缺陷**（移动端入口消失、键盘失效），而不是安全漏洞。
